# Core Concepts

Understanding Qefro begins with five fundamental architectural concepts:

---

## 1. AI Workspaces & Tenancy

| Concept | Summary | Read more |
| --- | --- | --- |
| **Organization (Tenant)** | Top-level customer boundary. Encapsulates teams, billing, and global Customer Hub People. | [Organizations](/docs/platform/organizations) |
| **AI Workspace** | Isolated operational context. Owns dedicated knowledge collections, channel connections, tools, and Marketplace app installations. | [What is an AI Workspace?](/docs/concepts/what-is-an-ai-workspace) |
| **Customer AI vs Employee AI** | Customer-facing channels (Website Widget, WhatsApp, Instagram) vs Employee-facing Internal Portal. | [Customer vs Employee](/docs/concepts/customer-ai-vs-employee-ai) |
| **Hybrid RAG** | Document grounding combining dense semantic vectors (Zvec) and BM25 sparse keyword ranking with strict citations. | [Hybrid RAG](/docs/concepts/hybrid-rag) |
| **RBAC** | Organization-level roles (Owner, Admin, Member) and installation-level app RBAC. | [RBAC](/docs/platform/rbac) |

## 2. Marketplace Apps vs External System Integrations

Qefro enforces two distinct execution paradigms:

| Dimension | Metadata Marketplace App | External System Integration |
|---|---|---|
| **Primary Role** | Domain applications owned and executed by Qefro (Hospitality, Clinic, Real Estate, Appointments). | Connecting existing systems of record (Focus ERP, ERPNext, Odoo, custom backends). |
| **Format** | Declarative metadata package (`manifest.yaml`, `entities/`, `workflows/`, `ui/`, `events/`). | Signed HTTPS webhook bridge or REST/OpenAPI tool definitions. |
| **Hosting & Execution** | **`hosting: runtime`** — executed natively by **Qefro Runtime**. No app server or Docker container. | Customer/third-party infrastructure running the Qefro Backend SDK (`POST /qefro`) or REST API. |
| **Data Plane** | Managed runtime storage triple-keyed to `(tenant_id, workspace_id, installation_id)`. | External database managed by the customer's ERP or backend. |
| **Developer Journey** | `qefro app init` ➔ metadata authoring ➔ `validate` ➔ `package` ➔ `publish`. | Implement SDK handlers ➔ run service ➔ register SDK Connection in Workspace. |

Learn more: **[Runtime vs SDK](/docs/solutions/runtime-vs-sdk)** · **[Integration Decision Guide](/docs/developer/integration-models)**.

## 3. Qefro Runtime & FlowRunner

| Concept | Summary | Read more |
|---|---|---|
| **Qefro Runtime** | The unified engine executing chat turns, RAG retrieval, FlowRunner state transitions, entity CRUD, and event dispatch. | [Runtime Architecture](/docs/developer/concepts/runtime) |
| **FlowRunner** | Deterministic multi-step business workflow engine. Orchestrates steps (ask, tool, message, condition, approval, challenge). | [FlowRunner](/docs/developer/concepts/flows) |
| **Runtime Actions** | Secure execution capabilities (`entity.<id>.create`, `execution: runtime` or HTTP calls). Governed by runtime authority checks. | [Business Actions](/docs/concepts/business-actions) |
| **Action Authority** | Independent security boundary. Unconditionally strips caller authority parameters and verifies permissions before execution. | [AI Agent Security](/docs/concepts/ai-agent-security) |
| **Business Events** | Standardized JSON envelopes emitted onto the PostgreSQL event bus triggering automations and flows. | [Events](/docs/developer/concepts/events) |

## 5. Security & Trust Principles

1. **The model is not the authority boundary:** LLMs propose candidate parameters; the runtime strictly validates, strips forbidden authority keys, and authorizes actions.
2. **Triple-keyed storage isolation:** Every Marketplace record requires `(tenant_id, workspace_id, installation_id)`.
3. **Encrypted secrets at rest:** All API tokens and integration credentials are encrypted with AES-256-GCM.
4. **HMAC Webhook Signatures:** Platform-to-SDK calls and Meta webhooks require cryptographic signature verification.
